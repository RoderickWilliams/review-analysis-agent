# 抖音采集与筛选

仅在需要从抖音主页采集时读取。已有评论材料直接回主流程分析，不重新采集。流程参考小马 Pro / XiaoMaAnn 的主页候选—分层选作品—五条一批—可见评论采集方法，本文已写全执行约定，不依赖对方Skill或本机路径。分析仍使用本Skill的情绪、讨论、具体处境与追问逻辑。

## 1. 打开主页并核对账号

使用当前环境提供的正常浏览器控制工具，先读取工具文档，再用其支持的导航、页面读取、点击与滚动操作；不假设特定插件或某个旧版本的浏览器API已安装。用户指定浏览器时按其选择，否则使用可用的用户可见浏览器。不要调用只适用于语音通话的屏幕读取工具。

- 打开用户提供的主页链接，记录可见昵称、账号标识、简介和公开内容领域；确认后续作品属于这位作者。短链通过正常导航解析。
- 如果链接打开的是单条视频，沿可见作者入口进入主页并核对；有多个可能作者时才向用户确认。不把单条视频的评论当成账号研究。
- 无浏览器控制能力时说明本次无法代采，可以接收用户导出评论继续；不能用搜索摘要充当采集结果。
- 出现登录或验证时保留当前位置，提示用户在浏览器完成；不索取密码、验证码或Cookie。验证码、访问限制、反复空白或账号不符时停止当前采集，不绕过平台限制。

在本次任务输出目录建立持久采集子目录，保存候选、已选作品、逐篇评论和进度；不要把临时目录作为唯一副本。只读公开资料，不点赞、关注、收藏、发评论、发消息或改变账号设置。不读取Cookie、浏览器存储、隐藏接口或私有网络请求。

## 2. 先筛作品，再读评论

默认以采集当天为准查看近90天的公开作品；用户明确指定近一年或其他范围时遵从，不再重复确认。候选不足30条就用实际可读数量，不为凑数自动扩展时间。记录当前实际浏览到的候选范围，不能把未翻到的作品写成已筛完。

正常浏览主页卡片，保存可见标题/文案、日期、置顶状态、作品ID或公开链接、点赞数、评论数。缺失信息记未知；相对日期保留原显示及采集日期，不编造精确时间。置顶作品可在默认90天之外，最多3条并标明超出窗口。非置顶日期不明的先打开核验；仍不明的单列待核实，不算作已确认在时间范围内。遇到一条旧置顶不能认定已翻完近90天。

作品选择顺序：

1. **置顶代表作，最多3条。**观察作者重点展示的内容。
2. **高互动作品，最多10条。**从其余时间范围内作品中选。如果候选都能看到评论量，优先按评论量比较、点赞辅助；只能一致看到点赞时用点赞作初筛，并记下限制。不能把点赞数冒充评论量。
3. **普通作品，补足至最多30条。**从剩余候选中分散选取不同日期和主要主题的内容，避免只看爆款，也避免一个热点的多个切片占满样本。同一条只能占一个位置，不重复计入置顶和高互动。

标题、简介和可见主题用于初筛，评论的具体价值要进入页面后才判断。不看评论前就写“多人求方法”“评论集中吐槽”等未经观察的入选理由。没有逐字稿时，也不要虚构视频内容。

**题材与排除：**优先作者实际内容领域中的问题解释、经验分享、观点分歧与案例。排除直播入口、不可访问作品、纯外部广告，以及与其专业内容明显无关且只适合看造型的随拍；后一类若有助于理解观众形象期待，可留作第一部分辅助，标明用途，不挤占主样本。仅凭“产品”“咨询”“创业”等词不认定广告；相关产品体验、购买问题、服务反馈本身可以有研究价值，保留时说明其商业背景。高情绪或争议不等于低信息量，不能据此整篇跳过。

若进入作品后才发现无评论、纯无关刷屏或只剩非专业闲聊，记录实际观察与去向，需要时从已存候选补位；不要反复重扫主页。采集期间做是否适用的简单判断即可，完整需求归因留到材料合并后。

## 3. 分批采集：先保留原话，不按高赞截断

每5条作品为一批，仅是内部执行与保存节奏。成功时自动继续，不让用户每5条点一次确认。串行使用一个内容页，避免并发打开大量平台页面。

每条作品：

1. 等待可见标题/评论容器，读取当前已加载、浏览器工具允许访问的公开评论。工具支持批量读取时一次读取当前评论容器，避免逐条点开；只用实际观察到的页面结构，不猜接口或选择器。
2. 沿平台默认顺序读取首批评论，再做最多两次正常向下滚动或“加载更多”，每次等待可见内容变化后保存。即默认最多三批可见一级评论；少于三批或到达结尾就按实际数量记录。无变化时不无限滚动。
3. 保留这几批中实际读到的评论，记录原文、可见点赞、作者标记和显示顺序；不再次只取高赞30条。低赞但明确的问题、具体体验与反对意见一样保留。
4. 可见回复一起保留。对于有具体追问、分歧或需要作者回应补上下文的评论，默认每篇选最多3个回复串，分别做一次正常展开并保留读到的回复及其父评论；不无限追开全部楼层。其他尚未展开回复标注未采集，不当作不存在。用户明确要求更多且浏览器可正常访问时再扩展。
5. 记录本篇真实采集范围和状态，保存后处理下一篇。遇到普通加载失败可有限重试当前作品，累计不超过3次；遇到验证/访问限制直接暂停。失败项目保留原因，已成功作品不重采。

三批评论与三组回复是默认可控样本范围，不是“已采完所有评论”的承诺。用户指定完整采集时先按页面实际可访问程度执行并持续保存，未采完的必须写明，不能沿用默认上限却声称完整。

未知点赞为null，不填0。原文中的缩写、表情与立场不改写；图片评论仅记录可读信息并注明图片。作者回复只做上下文，不算观众需求。优先用可见稳定ID去重；没有时用同篇、显示作者、原文及可确认的重复加载关系判断，不能把不同人的相同问题合并。若平台没显示稳定ID，生成本地ID并注明，不能冒充平台评论ID。

## 4. 保存、续跑与进入现有分析

在采集子目录维护以下文件，均由AI生成，用户无需准备：

- `candidates.json`：账号、采集日期、默认/指定时间范围，候选作品及可见指标，已知排除原因。
- `selected.json`：入选作品、本地/平台ID、分组（pinned/high_interaction/ordinary）、选择理由、是否超出窗口。
- `progress.json`：各作品 pending/ok/partial/failed/blocked 状态、尝试次数、已读批次、停止原因及原始文件路径。
- `raw/<作品ID>.json`：本篇实际可见标题、日期、公开链接、正文可用片段、评论记录（本地ID、可见平台ID、原文、点赞、父ID、作者标记、显示顺序）。用户可见昵称仅作必要去重依据，不扩展采集私人信息。

公开链接落盘前去除追踪、分享令牌和会话类参数，保留用于定位公开账号/作品的必要ID。恢复时先读进度，仅接着处理未完成作品；partial从最后保存处续采并去重，不丢已采材料。评论变化时保留可核对的原记录，不悄悄覆盖成另一份。

每批完成保存进度，简短说明已完成作品数与实际读到的评论数。执行较久时正常更新进展，不因为等待凑齐5条而长时间静默。平台阻塞时先保留材料：已有资料可以分析就继续做可完成部分并注明缺口；一条有效评论也没有时说明停在哪一步，不生成伪装完成的报告。

采集结束，合并实际原话，再进入主Skill第1步清洗、第2—4步归类分析、第5步生成报告。不要调用小马的高赞截取、只计一级评论、固定需求等级或报告渲染器来替换我们的方法。映射为`references/report-data.md`格式时保留回复关系、作者标记与可追溯位置；作品采集范围写入`contents[].note`，总体范围写入`material_note`，详细缺口和采集方式写入`processing_notes`。报告的条数仍由实际记录计算，不能用平台显示的评论总数补齐。
